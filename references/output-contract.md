# 输出内容契约

## 第一份：`study_handbook`

作用是快速检索、复习、行动和应对提问。优先使用清晰标题、短段落、真正可比较的表格、带答案的问题库和复习计划。

至少包含：目标与范围、来源与证据状态、内容地图、优先级、核心知识或工作链条、常见失败、可能被问的问题及答案、时间化行动计划、最终检查表。具体章节由场景手册决定，不能使用完全相同的固定目录。

问题库不得只有题目。每道题必须给出以下一种内容：可直接复习的参考答案、需要按材料调整的作答框架，或在证据不足时明确标注 `UNKNOWN` 的回答边界。面试和汇报答案只能使用用户真实证据；不得把示范措辞写成用户已经完成的经历。

事实、建议和示范表述必须分开。事实保留证据标签；建议不得伪装成用户已经具备的经历或已经发生的结果。

## 第二份：`teaching_narrative`

作用是让用户像学生听老师讲课一样真正理解内容。作者站在耐心、经验丰富的老师或直属上级角度，直接面对学习者讲解，从学习者现有基础出发，逐步回答“为什么要学、它是什么、如何运作、怎样判断、哪里容易错、实际怎么用”。

正文以自然连续的段落为主，语气耐心、具体、循序渐进，允许使用贴近当前材料的类比和例子。只在步骤、条件或对比无法用短段落清楚表达时使用少量列表或表格。不得把第一份文档改写成另一份提纲，不得堆砌“重点一、重点二”，也不得把全文写成问答列表。

讲解应包含通俗理解、必要的严格解释、概念之间的因果联系、例子、失败情况、现实用途和理解检查。短版/长版表达可以在讲解完成后作为收束内容，但不能取代主体讲解。

## 第三份：`practice_guide`

只在 `practice_needed=true` 时生成。内容必须与当前任务中的真实实操要求对应。

每项练习应包含：任务与约束、环境和前置条件、最简单正确方法、必要时的改进方法、完整代码/查询/命令或设计产物、决策型注释、正常/边界/失败检查、复杂度或容量推理、替代方案、追问、部分完成时的诚实表达。

代码不得声称来自用户项目，除非已核验来源和作用。命令未实际执行时标记 `UNVERIFIED`。系统设计应明确需求假设、容量假设、接口、数据、故障、权衡和可观测性。

## 输出数量决策

| 情形 | 手册 | 讲解稿 | 实操指南 |
|---|---:|---:|---:|
| 一般知识点、理论考试、普通会议 | 是 | 是 | 否 |
| 代码/SQL/数据/实验操作考试 | 是 | 是 | 是 |
| 一般岗位或行为面试 | 是 | 是 | 否 |
| 明确含编程、调试或系统设计的面试 | 是 | 是 | 是 |
| 熟悉流程、职责或业务 | 是 | 是 | 否 |
| 需要操作代码库、查询、部署或排障 | 是 | 是 | 是 |
| 周进展或普通组会汇报 | 是 | 是 | 否 |
| 需要代码走读、实验复现或现场演示 | 是 | 是 | 是 |

用户明确只要一份文档时服从用户要求；“完整准备包”仍遵守第三份按需规则。不要为了凑够三份文档生成空洞内容。

配置规则：

- `output_mode=full_pack`：必须包含手册和讲解稿；`practice_needed=true` 时还必须包含实操指南。
- `output_mode=selected`：`requested_documents` 与 `documents` 中的文档类型必须完全一致，可以只生成一份。
- `practice_needed=false` 时任何模式都不得生成实操指南。
- 只要求聊天分析、审查或演练时不调用生成器，也不创建空配置占位。

## 证据账本

当事实可追溯性对任务有价值时，在顶层 `evidence` 中为每项证据分配唯一 ID、状态、事实或结论以及来源。使用 `evidence_table` 块选择要展示的 ID。来源写材料名称、稳定链接、页码、代码位置或运行记录；不要写个人绝对路径、凭据或无法公开的链接。
